#### **二、 详细实现分析**

**1. WebView 的初始化与配置 (`viewDidLoad`)**

-   **控制器**: `SMLoginViewControllerV2` 继承自一个名为 `XWebController` 的基类，它内部封装了 `WKWebView`。
-   **内容拦截规则 (Content Blocker)**:

    -   通过 `WKContentRuleListStore.default().compileContentRuleList` 编译并应用到 `WKWebView` 的 `configuration` 中。
-   **加载初始页面**:
    -   在内容拦截规则配置成功后的回调里，WebView 开始加载 `https://m.newsmth.net/index`。

**2. 页面加载完成后的交互 (`webView:didFinish:`)**

当 `WebView` 完成页面加载后，App 会通过 `evaluateJavaScript` 方法向页面注入一段 JS 脚本，用于改善用户体验和实现特定功能。

-   **JS 脚本主要功能**:
    -   **DOM 元素隐藏 (已注释)**: 代码中预留了隐藏广告容器 (`#ad_container`)、logo、菜单等元素的逻辑，但当前被注释掉了。
    -   **调整样式**: 放大登录表单区域 (`#u_login`) 的字体，方便用户输入。
    -   **自动填充**:
        -   从 `window.localStorage` 中读取键为 `_xsmth_userinfo` 的数据。
        -   如果存在，则解析出 `id` 和 `passwd` 并自动填充到对应的输入框中。
    -   **保存用户输入**:
        -   监听真人验证按钮 (`#TencentCaptcha`) 的点击事件。
        -   当用户点击该按钮时，将当前输入框中的 `id` 和 `passwd` 保存到 `window.localStorage` 中，键依然是 `_xsmth_userinfo`。这确保了下次登录时可以自动填充。
    -   **强制登录 (可选)**: 如果 `SMConfig.enableForceLogin()` 为 `true`，脚本会自动点击真人验证按钮，可能用于实现某种程度的自动登录。
    -   **主题适配**: 将网页的文字颜色设置为与 App 主题色一致。

**3. 导航拦截与 Cookie 获取 (`webView:decidePolicyFor:decisionHandler:`)**

这是实现登录状态捕获的核心所在。该方法会在 `WebView` 的每一次页面跳转前被调用。

-   **逻辑判断**:
    -   首先，代码会判断请求的 `URL host` 是否为 `m.newsmth.net`。登录成功后的跳转通常仍在此域名下。
    -   如果是，则执行 Cookie 获取逻辑。
-   **Cookie 获取与处理**:
    1.  通过 `self.webView.configuration.websiteDataStore.httpCookieStore.getAllCookies` 异步获取当前 `WebView` 中的所有 `Cookie`。
    2.  遍历 `Cookie` 列表，筛选出对我们有用的登录凭证。
    3.  **筛选条件**:
        -   `domain` 必须是 `.newsmth.net`。
        -   `name` 必须是以下三者之一：`main[UTMPNUM]`, `main[UTMPKEY]`, `main[UTMPUSERID]`。这三个是水木社区用来标识用户登录状态的核心 `Cookie`。
    4.  **Cookie 持久化**:
        -   对于筛选出的登录 `Cookie`，代码会重新创建一个 `HTTPCookie` 对象，并设置一个较长的过期时间（至少7天），然后通过 `HTTPCookieStorage.shared.setCookie(c!)` 将其存入 App 的全局 `Cookie` 存储区。
        -   **关键点**: 存入 `HTTPCookieStorage` 后，App 内所有使用标准网络库（如 `URLSession`）发起的对 `newsmth.net` 的请求，都会自动带上这些 `Cookie`，从而实现了 App 的 "登录状态"。
-   **确认登录状态**:
    -   在处理完 `Cookie` 后，代码会调用 `SMAccountManager.instance()?.setCookies(cookies)`，让账户管理单例类也拿到这些 `Cookie`。
    -   接着检查 `SMAccountManager.instance()?.isLogin`。这个 `isLogin` 属性的 `true/false` 就是判断登录是否成功的最终依据（其内部逻辑很可能是检查是否存在上述三个关键 `Cookie`）。
    -   如果 `isLogin` 为 `true`，则调用 `self?.loginSuccess()`。

**4. 登录成功处理 (`loginSuccess`)**

-   当确认登录成功后，此方法被调用。
-   它会执行外部传入的成功回调 (`successFunc` 或 `target`/`selector`)。
-   最后，关闭当前的登录视图控制器 `self.close()`，流程结束。

### **App 会话管理及重新登录机制分析**

#### **1. 如何验证 Session (会话) 是否失效？**

App 并不是在每次操作前都去请求服务器“验证”一下，而是通过**被动地检查本地存储的 Cookie 状态**来判断。这个核心逻辑位于 `SMAccountManager.m` 中。

1.  **关键的 Cookie**: 水木社区的登录状态由一个名为 `main[UTMPUSERID]` 的 `Cookie` 决定。
    *   如果这个 `Cookie` 的值是用户的 ID (例如 "myid")，则认为已登录。
    *   如果值是 `guest`，或 `Cookie` 本身已根据其 `expiresDate` 过期，则认为登录已失效。

2.  **检查时机**:
    *   **App 启动或从后台返回时**: `SMAccountManager` 会加载并检查本地 `NSHTTPCookieStorage` 中的 `Cookie`，根据上述规则判断 `isLogin` 状态。
    *   **每次网络请求后**: 在新的网络层 `SMNetwork.swift` 中，代码会监控所有网络请求的响应头。如果响应头 (`Set-Cookie`) 中包含了 `main[UTMPUSERID]`，意味着登录状态可能发生了变化（例如，在另一个设备上登出导致当前 session 失效），这时会触发 `SMAccountManager` 的 `refreshStatus` 方法，重新检查 `Cookie` 来更新登录状态。
    *   **WebView 交互中**: 在 `WebView` 登录流程里，一旦包含关键 `Cookie`，也会调用 `SMAccountManager` 的方法来更新状态。

3.  **静默自动重连 (Auto Login)**:
    *   在 `SMAccountManager.m` 中，如果检查 `Cookie` 发现登录已失效 (`name` 变为 `nil`)，它会触发一次 `autoLogin`。
    *   `autoLogin` 方法会尝试从 `MMKV` 中读取用户之前保存的用户名和密码，然后在后台静默地向登录接口发送一次 `POST` 请求。
    *   **目的**：如果用户只是 `Cookie` 过期，而密码没变，App 可以通过此方式自动为用户延续 `Session`，用户对此过程无感知，体验最好。

**小结**：Session 失效的判断是基于对关键 `Cookie` 的状态检查，这种检查在 App 生命周期和网络活动中频繁发生。一旦发现失效，会优先尝试静默地自动重连。

#### **2. Session 失效后，如何让用户重新登录？**

如果静默的 `autoLogin` 失败了（比如用户修改了密码），用户就处于事实上的登出状态。此时 App 不会立刻弹出登录窗口，而是在用户**下一次执行需要登录权限的操作时**，才会触发用户交互的登录流程。

这个机制的实现非常优雅，主要体现在 `SMViewController.m` 这个所有视图控制器的基类中：

1.  **提供统一的登录入口方法**: `SMViewController` 中定义了两个关键方法：
    *   `performSelectorAfterLogin:(SEL)aSelector`
    *   `afterLoginSuccess:(void(^)())success fail:(void(^)())fail`

2.  **典型的调用场景**: 假设用户要“发帖”。发帖按钮的目标方法是 `doPost()`, 但它不会直接被调用。代码会这样写：
    ```objective-c
    [self performSelectorAfterLogin:@selector(doPost)];
    ```

3.  **内部逻辑判断**: `performSelectorAfterLogin:` 方法的内部逻辑是：
    *   **第一步：检查登录状态**
        ```objective-c
        if ([SMAccountManager instance].isLogin) { // 如果已登录
            // 直接执行后续操作
            [self performSelector:aSelector withObject:nil afterDelay:0];
        } else { // 如果未登录
            // 执行第二步
        } 
        ```
    *   **第二步：调起登录页面**
        ```objective-c
        // 创建 SMLoginViewControllerV2 (我们之前分析过的 WebView 登录页)
        SMLoginViewControllerV2 *vc = [SMLoginViewControllerV2 new];
        
        // **最关键的一步**: 将原本要执行的操作 (doPost) 作为“登录成功后的回调”传给登录页面
        [vc afterLoginWithTarget:self selector:aSelector];
        
        // 以模态框的形式弹出登录页
        P2PNavigationController *nvc = [[P2PNavigationController alloc] initWithRootViewController:vc];
        [self presentViewController:nvc animated:YES completion:nil];
        ```

4.  **完成闭环**:
    *   用户在弹出的登录页中成功登录。
    *   登录成功后，`SMLoginViewControllerV2` 会执行之前设置好的回调，也就是 `doPost` 方法。
    *   登录页面关闭，原来的发帖操作得以继续执行，整个流程对用户来说非常自然。

**总结**：App 通过一个**前置检查和回调机制**来处理需要登录的场景。它不关心 `Session` 何时失效，只在用户需要用它的时候检查。如果 `Session` 无效，就暂停当前操作，插入一个登录流程，登录成功后再自动恢复之前的操作。这种“按需登录”的设计极大地提升了用户体验。

这套机制在整个 App 中被广泛复用，确保了所有需要权限的操作都能得到统一和正确的处理。
